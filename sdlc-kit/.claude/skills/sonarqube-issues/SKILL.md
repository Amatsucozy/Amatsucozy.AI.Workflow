# SonarQube Issues Listing

Uses the SonarQube MCP server; operation names below (`list_pull_requests`,
`search_sonar_issues_in_projects`, …) are what to look up — take the real
prefix and parameter names from the loaded schemas. If the server isn't
registered or needs authorization, say so and stop.

## 1. Resolve the project key

1. Get the GitHub org from `git remote -v` (the path segment before the repo
   name), lowercased.
2. Check this skill's cached map at `resources/projects/<org>/map.md` (beside
   this SKILL.md; generated by `sonarqube-project-map` from a fixed template):
   - Repo under "Mapped projects" → use that key; go to step 2.
   - Under "GitHub repos with no SonarQube project" → report no coverage.
   - Under "Unmapped — verify manually" → unresolved, not a match.
3. No map, repo not listed, or the map looks stale → resolve live, stopping at
   the first confident hit:
   1. `projectKey` in `.sonarlint/connectedMode.json` (workspace root or a
      parent).
   2. `sonar.projectKey` in `sonar-project.properties`, `pom.xml`,
      `build.gradle(.kts)`, or `package.json`.
   3. `sonar.projectKey` in CI files (`.github/workflows/*.yml`,
      `Jenkinsfile`, `.gitlab-ci.yml`, `azure-pipelines.yml`,
      `.circleci/config.yml`).
   4. `search_my_sonarqube_projects` with the project the user named, else a
      query from the remote or folder name.
   Then suggest running `sonarqube-project-map`; don't write the map from here.
4. A wrong key silently returns another project's issues: check the resolved
   project's name against the repo. Several plausible candidates → ask.

## 2. Branch vs. pull request

1. `git branch --show-current`, then `list_pull_requests` for the key.
2. A PR whose `branch` equals the git branch → pass its `key` as
   `pullRequest`.
3. No match: for a long-lived branch (`main`, `develop`, `master`, the
   project default) or an explicit branch-level request, confirm via
   `list_branches` and pass it as `branch`. Otherwise report that no analysis
   exists for this branch yet — never fall back to an unrelated one.
4. Never pass a git branch name as `pullRequest`, or set both parameters.

## 3. Query, fully paginated

`search_sonar_issues_in_projects` with `projectKeys: [<key>]`, the
`pullRequest` or `branch`, `issueStatuses: ["OPEN", "CONFIRMED"]` (widen only
when asked for resolved/all), and any user filters (`severities`,
`impactSoftwareQualities`). Page with `pageIndex` until
`pageIndex * pageSize >= paging.total`. If the harness saves a large response
to an overflow file, read the file, not the preview.

## 4. Summarize

- Header: git branch → project key → PR key or branch → total issues.
- A count table for the severities present (`BLOCKER`…`INFO`, or
  `HIGH`/`MEDIUM`/`LOW`/`INFO` for software-quality severities).
- By rule: message, count, distinct files (`component` minus the
  `<projectKey>:` prefix). CRITICAL/BLOCKER and security-impacting first.
- Over ~30 issues: group rather than enumerate keys; offer raw keys or one
  rule's occurrences on request.

## 5. Only if asked

- Security Hotspots: `search_security_hotspots` (same key/branch/PR
  parameters).
- Status changes go through `change_sonar_issue_status`, which mutates
  SonarQube. Confirm the exact issue keys and target status with the user
  first, and never do it as part of a listing.

Org-specific keys and repo names belong in the map file, never in this one.
