# SonarQube Issues Listing

## When to use

- "list/show sonarqube issues for this branch/PR"
- "what's sonar complaining about on this branch"
- "give me a breakdown of sonar findings before I open the PR"
- Any request to inspect SonarQube-reported bugs, vulnerabilities, code
  smells, or security hotspots for the code currently checked out.

Not for changing issue status (accept / false-positive / reopen) — that is a
separate, explicit mutating action (Step 5), never bundled into a listing.

## Prerequisites

- The SonarQube MCP server's tools are deferred. Load them with ToolSearch
  (`+sonarqube <operation>`) before the first call and read the returned
  schemas — the prefix (`mcp__sonarqube__…`) and parameter names come from
  the registration, never from memory. Operation names below
  (`list_pull_requests`, `search_sonar_issues_in_projects`, …) are what to
  search for.
- Server not registered or needing authorization → say so and stop; never
  fabricate results.

## Workflow

### 1. Resolve the SonarQube project key

1. Derive the GitHub org from `git remote -v` (the path segment right before
   the repo name: `.../acme-corp/api-service.git` → `acme-corp`). Lowercase
   it for the lookup below.
2. Check for a cached map at `resources/projects/<org-lowercase>/map.md`
   under this skill's own directory (the folder holding this SKILL.md —
   `.claude/skills/sonarqube-issues/` in the project, or the user-level
   skills dir). It is generated by the `sonarqube-project-map` skill from a
   fixed template, so its section headers are stable. If it exists:
   - "Mapped projects" table lists the current repo → use that key and skip
     to Step 2; no live query needed.
   - "GitHub repos with no SonarQube project" lists it → the repo has no
     coverage; report that without a live query.
   - "Unmapped — verify manually" lists it → unresolved, not a match.
3. No map for this org, repo in neither list, or the map looks stale → live
   resolution, stopping at the first confident hit:
   1. `projectKey` in `.sonarlint/connectedMode.json` (workspace root or a
      parent directory).
   2. `sonar.projectKey` in `sonar-project.properties`, `pom.xml`,
      `build.gradle(.kts)`, or `package.json` at the repo root.
   3. `sonar.projectKey` in CI files (`.github/workflows/*.yml`,
      `Jenkinsfile`, `.gitlab-ci.yml`, `azure-pipelines.yml`,
      `.circleci/config.yml`).
   4. User named a project → `search_my_sonarqube_projects` with `q=<name>`;
      pick the exact/closest key.
   5. Otherwise `search_my_sonarqube_projects` with a query derived from the
      git remote or repo folder name.
4. A wrong key silently returns another project's issues — sanity-check the
   resolved key's project name against the repo before querying. More than
   one plausible candidate → ask the user; never guess.
5. If you fell back to live resolution because no map (or a stale one)
   exists, say so and suggest running `sonarqube-project-map` to generate or
   refresh it. Do not write that resource file from here — that skill owns
   it.

### 2. Determine branch vs. pull-request context

1. `git branch --show-current` → the git branch name.
2. `list_pull_requests` with the resolved `projectKey`.
3. The PR whose `branch` equals the git branch → its `key` is the
   `pullRequest` parameter for later calls.
4. No PR matches:
   - Long-lived branch (`main`, `develop`, `master`, the project default), or
     the user explicitly wants branch-level analysis → confirm the name via
     `list_branches` and pass it as `branch`.
   - Otherwise tell the user no SonarQube PR/branch analysis exists yet for
     this branch — never fall back to an unrelated branch or PR.
5. Never pass a git branch name as `pullRequest`, and never set both `branch`
   and `pullRequest` on the same call.

### 3. Query issues, fully paginated

Call `search_sonar_issues_in_projects` with:

- `projectKeys: [<key>]`
- `pullRequest` or `branch` from Step 2
- `issueStatuses: ["OPEN", "CONFIRMED"]` by default (excludes
  `FALSE_POSITIVE` / `ACCEPTED` / `FIXED`) — widen only when the user asks
  for resolved/closed/all issues.
- Any user-specified filters: `severities`, `impactSoftwareQualities`.

Read `paging.total` and `paging.pageSize` from the first response, then
increment `pageIndex` until `pageIndex * pageSize >= total`. Never report an
incomplete count from page 1.

A large response may be persisted to an overflow file by the tool harness —
Read that file instead of summarizing the visible preview, or issues are
silently dropped from the report.

### 4. Summarize, don't dump

- Header: git branch → resolved project key → PR key or branch used → total
  issue count.
- A severity/count table with whatever severities are present
  (`BLOCKER`/`CRITICAL`/`MAJOR`/`MINOR`/`INFO`, or `HIGH`/`MEDIUM`/`LOW`/
  `INFO` for software-quality severities).
- A breakdown by `rule`: human-readable message, issue count, and the
  distinct files (`component` with the `<projectKey>:` prefix stripped).
- CRITICAL/BLOCKER and SECURITY-impacting issues first.
- Roughly >30 issues → don't enumerate every key; group by rule/file/severity
  and offer raw keys or a single rule's occurrences on request.

### 5. Optional follow-ups (only if explicitly asked)

- Security Hotspots are a separate concept — `search_security_hotspots`
  (same `projectKey`/`branch`/`pullRequest` parameters), not the issues
  search.
- Status changes (`accept`, `falsepositive`, `reopen`) go through
  `change_sonar_issue_status`. It mutates SonarQube state — confirm the exact
  issue key(s) and target status with the user first; never as a side effect
  of a listing.

## Guardrails

- Never guess a project key or PR key when resolution is ambiguous — ask.
- A git branch name and a SonarQube PR key are different identifiers;
  `pullRequest` wants the key from `list_pull_requests`, not the branch.
- Never report only page 1 when `paging.total` exceeds `paging.pageSize`.
- Never call `change_sonar_issue_status` as part of a listing request.
- No org-specific keys or repo names in this file — that data lives in
  `resources/projects/<org>/map.md`, owned by `sonarqube-project-map`.

## Example

```
git remote -v → .../acme-corp/api-service.git → org "acme-corp"
resources/projects/acme-corp/map.md → Mapped: acme-corp/api-service → acme-corp_api-service
git branch --show-current → feature/PROJ-123-add-retry-logic
list_pull_requests(projectKey="acme-corp_api-service") → PR 482 on that branch
search_sonar_issues_in_projects(projectKeys=["acme-corp_api-service"],
  pullRequest="482", issueStatuses=["OPEN","CONFIRMED"])
  → paging.total = 87, pageSize = 50 → fetch pageIndex 1 and 2

Report: 1 CRITICAL (cognitive complexity), 32 MAJOR (mostly "pass the
cancellationToken"), 43 MINOR (mostly "overloads should be adjacent"), 11 INFO.
```

Without a map.md for the org, the same flow falls back to live discovery for
the project key and ends by suggesting `sonarqube-project-map`.
