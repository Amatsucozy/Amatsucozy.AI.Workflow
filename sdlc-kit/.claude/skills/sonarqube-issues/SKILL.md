# Skill: SonarQube issues listing

## When to use

- "list/show sonarqube issues for this branch/PR"
- "what's sonar complaining about on this branch"
- "give me a breakdown of sonar findings before I open the PR"
- Any request to inspect SonarQube-reported bugs, vulnerabilities, code
  smells, or security hotspots for the code currently checked out.

Not for: changing issue status (accept/false-positive/reopen) — that is a
separate, explicit mutating action (see Step 5), never bundled into a
listing request unless the user asks for it directly.

## Prerequisites

- Confirm the `sonarqube` MCP server is available via `mcp_list_servers` if
  unsure it's configured.
- Always call `mcp_list_tools` for `server_name: sonarqube` at least once
  before the first `mcp_call_tool` invocation in a session — do not guess
  tool names or input schemas from memory, they can change.

## Workflow

### 1. Resolve the SonarQube project key

1. Derive the GitHub org from `git remote -v` (the path segment right
   before the repo name, e.g. `.../acme-corp/api-service.git` → org
   `acme-corp`). Lowercase it for the resource lookup below.
2. Check for a cached project map at this skill's own
   `resources/projects/<org-lowercase>/map.md` (relative to the directory
   containing this `SKILL.md` — find that directory from this skill's
   `source:` path in the available-skills listing, don't assume a fixed
   absolute path). It's generated by the `sonarqube-project-map` skill
   from that skill's `resources/template.md`, so it always has the same
   section headers below — see that template if a map.md ever looks
   malformed. If it exists:
   - Its "Mapped projects" table is a fast path: if the current repo is
     listed, use that key directly and skip to Step 2 — no live SonarQube
     query needed.
   - Its "GitHub repos with no SonarQube project" list tells you when a
     repo has no coverage, without a live query either.
   - Its "Unmapped — verify manually" section means the map's author
     wasn't confident — treat those repos as unresolved, not as a match.
3. If no map exists for this org, the repo isn't in either list, or the
   map looks stale/wrong, fall back to live resolution, stopping at the
   first confident hit:
   1. `.sonarlint/connectedMode.json` in the workspace root or a parent
      directory → `projectKey` field.
   2. `sonar.projectKey` in `sonar-project.properties`, `pom.xml`,
      `build.gradle`, `build.gradle.kts`, or `package.json` at the repo
      root.
   3. `sonar.projectKey` in CI files: `.github/workflows/*.yml`,
      `Jenkinsfile`, `.gitlab-ci.yml`, `azure-pipelines.yml`,
      `.circleci/config.yml`.
   4. If the user names a project, call `search_my_sonarqube_projects`
      with `q=<name>` and pick the exact/closest key.
   5. Otherwise call `search_my_sonarqube_projects` with a query derived
      from the git remote or repo folder name.
4. An incorrect project key silently returns issues for the wrong project
   — sanity-check the resolved key's project name against the repo before
   querying. If more than one candidate plausibly matches, ask the user to
   disambiguate rather than guessing.
5. If you had to fall back to live resolution because no map (or a stale
   one) exists for this org, say so in your response and suggest running
   the `sonarqube-project-map` skill to generate/refresh
   `resources/projects/<org-lowercase>/map.md` — don't write or edit that
   resource file yourself from here, that skill owns it.

### 2. Determine branch vs. pull-request context

1. Run `git branch --show-current` to get the current git branch name.
2. Call `list_pull_requests` with the resolved `projectKey`.
3. Find the pull request whose `branch` field equals the git branch name →
   use its `key` as the `pullRequest` parameter for later calls.
4. If no PR matches:
   - For a long-lived branch (`main`, `develop`, `master`, or the project's
     default) or when the user explicitly wants branch-level (not PR)
     analysis, use `list_branches` to confirm the branch name and pass it
     as `branch` instead.
   - Otherwise tell the user no SonarQube PR/branch analysis exists yet for
     this branch — don't silently fall back to an unrelated branch or PR.
5. Never pass a git branch name into the `pullRequest` parameter, and never
   set both `branch` and `pullRequest` on the same call — pick one based on
   the context you just resolved.

### 3. Query issues, fully paginated

Call `search_sonar_issues_in_projects` with:

- `projectKeys: [<key>]`
- `pullRequest` or `branch` from step 2
- `issueStatuses: ["OPEN", "CONFIRMED"]` by default (excludes
  `FALSE_POSITIVE`/`ACCEPTED`/`FIXED`) — only widen this if the user asks
  for resolved/closed/all issues too.
- Any user-specified filters: `severities`, `impactSoftwareQualities`.

Read `paging.total` and `paging.pageSize` from the first response, then
repeat with `pageIndex` incremented until `pageIndex * pageSize >= total`.
Do not stop at page 1 and report an incomplete count when more pages exist.

Large responses can get truncated by the tool harness into an overflow
file (`<truncation_notice>`) — always `read` that file rather than
summarizing from the visible snippet alone, or you will silently drop
issues from the report.

### 4. Summarize, don't just dump

Produce a report with:

- Header: git branch → resolved SonarQube project key → PR key or branch
  used for the query, and the total issue count.
- A severity/count table (whatever severities are actually present —
  `BLOCKER`/`CRITICAL`/`MAJOR`/`MINOR`/`INFO` on SonarQube Server, or
  `HIGH`/`MEDIUM`/`LOW`/`INFO` if using the software-quality severities).
- A breakdown grouped by `rule`, with the human-readable message, an issue
  count, and the distinct files (`component`, with the leading
  `<projectKey>:` prefix stripped) each rule appears in.
- CRITICAL/BLOCKER and SECURITY-impacting issues called out first.
- If the total is large (roughly >30), do not enumerate every single issue
  key inline — group by rule/file/severity and offer to list raw issue
  keys or a specific rule's occurrences on request.

### 5. Optional follow-ups (only if explicitly asked)

- Security Hotspots are a separate concept from issues — use
  `search_security_hotspots` (same `projectKey`/`branch`/`pullRequest`
  parameters), not `search_sonar_issues_in_projects`.
- To change an issue's status (`accept`, `falsepositive`, `reopen`), use
  `change_sonar_issue_status`. This mutates SonarQube state — confirm the
  exact issue key(s) and intended status with the user before calling it;
  never do this as a side effect of a listing request.

## Guardrails

- Never guess a project key or PR key when resolution is ambiguous — ask
  the user to disambiguate.
- A git branch name and a SonarQube pull request key are different
  identifiers; don't conflate them (`pullRequest` wants the SonarQube PR
  key from `list_pull_requests`, not the branch string).
- Never report only page 1 of results when `paging.total` exceeds
  `paging.pageSize` — page through everything before summarizing counts.
- Never call `change_sonar_issue_status` as part of a plain listing
  request.
- Don't hardcode any org's project keys or repo names into this file —
  that data belongs in `resources/projects/<org>/map.md`, generated and
  owned by the `sonarqube-project-map` skill, so this skill stays reusable
  across orgs and doesn't go stale in the prompt itself.

## Example

```
git remote -v → .../acme-corp/api-service.git
  → org "acme-corp" → resource lookup key "acme-corp"

read resources/projects/acme-corp/map.md
  → found; "Mapped projects" table has acme-corp/api-service → acme-corp_api-service
  → projectKey = "acme-corp_api-service" (no live SonarQube query needed)

git branch --show-current
  → feature/PROJ-123-add-retry-logic

list_pull_requests(projectKey="acme-corp_api-service")
  → PR 482, branch "feature/PROJ-123-add-retry-logic"

search_sonar_issues_in_projects(
  projectKeys=["acme-corp_api-service"], pullRequest="482",
  issueStatuses=["OPEN", "CONFIRMED"]
)
  → paging.total = 87, paging.pageSize = 50 → fetch pageIndex 1 and 2

Report: 1 CRITICAL (cognitive complexity), 32 MAJOR (mostly "pass the
cancellationToken"), 43 MINOR (mostly "overloads should be adjacent"),
11 INFO.

If `resources/projects/<org>/map.md` didn't exist, the flow above would
instead fall back to live discovery for the project key and suggest
running `sonarqube-project-map` afterward.
```
